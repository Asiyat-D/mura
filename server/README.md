# Mura: сервер доставки для Android и iOS 1.1

Этот сервер принимает только зашифрованные HPKE-конверты. Текст, пароли и закрытые ключи телефонов на сервер не передаются. Идентификаторы устройств и маршрутизация доступны серверу и оператору HTTPS-прокси.

Оба пользователя добавляют коды контактов друг друга. В коде находятся адрес сервера и открытые ключи; сверка кода безопасности с владельцем контакта защищает от подмены при передаче кода. Служба не ищет пользователей по номеру телефона и не выдаёт ключи собеседника.

## Текущий запуск на Mac

Адрес: **https://defense-arthritis-maritime-salvador.trycloudflare.com**. Он встроен в текущую iOS-сборку и может быть изменён в настройках Mura.

Сервер работает как две пользовательские службы launchd:

- `kz.mura.relay`: Python + SQLite, слушает только `127.0.0.1:8788`;
- `kz.mura.tunnel`: Cloudflare Quick Tunnel, HTTPS с обычной проверкой сертификата на телефонах.

Код, Python-окружение, SQLite и логи служб находятся в `~/Library/Application Support/MuraRelay/`. Параметры автозапуска — в `~/Library/LaunchAgents/kz.mura.{relay,tunnel}.plist`. Службы запускаются после входа владельца в macOS. Mac должен работать, не спать и иметь интернет. Настройки сна не изменяются.

Quick Tunnel — временный сервер разработки: адрес может смениться после перезапуска туннеля, а доступность не гарантируется. Новый адрес выводит команда `status`; его нужно указать на обоих телефонах. Содержимое SQLite сохраняется независимо от адреса. Для постоянного адреса нужен собственный HTTPS-хостинг или настроенный именованный туннель.

```sh
python3 server/mac-service.py status
python3 server/mac-service.py stop
```

Повторная установка / обновление служб из корня проекта:

```sh
python3 server/prepare.py
python3 server/mac-service.py install
```

`prepare.py` устанавливает Python-зависимость в отдельное окружение и проверяет SHA-256 официального `cloudflared` 2026.10.1 для Apple Silicon. `install` перезапускает только сервер, если туннель уже работает, сохраняя его текущий адрес. `stop` отключает только эти две службы; базу не удаляет.

## Протокол

- `POST /v1/register`: регистрация открытых ключей. ID = SHA-256(Ed25519 public key || X25519 public key). Владение ключом подтверждается подписью.
- `POST /v1/contacts` и `/v1/revoke`: разрешение / запрет корреспондента владельцем почтового ящика. Переписка требует взаимного добавления.
- `POST /v1/messages`: идемпотентная запись конверта по UUID. Повтор того же конверта не создаёт дубль, подмена с тем же UUID отклоняется.
- `GET /v1/inbox`: до 20 ожидающих конвертов, только для аутентифицированного получателя.
- `POST /v1/ack`: подтверждение после сохранения на устройстве. Получатель подписывает ID, отправителя, получателя и SHA-256 всего конверта ключом Ed25519. Сервер проверяет подпись и удаляет ciphertext, сохраняя квитанцию.
- `POST /v1/status`: состояние и подписанная квитанция. Отправитель сам проверяет подпись контакта; ответ сервера без правильной квитанции не превращается в «Доставлено».
- `POST /v1/erase`: удаление регистрации, контактов и серверных конвертов данного устройства.

Каждый запрос подписан Ed25519 по точным UTF-8-байтам:

```text
MURA-RELAY/1\nMETHOD\n/path\nDEVICE_ID\nTIMESTAMP\nNONCE_UUID\nSHA256_BODY_HEX
```

Допуск часов — 5 минут. Nonce одноразовый, хранится 10 минут и расходуется также при отказе выполнить подписанное действие. Для TLS-клиента запрещены перенаправления. Открытых HTTP-подключений на телефоне и ATS-исключений нет.

Неполученные конверты и квитанции хранятся до 7 дней; уборка выполняется при запросах и раз в минуту, пока сервер работает. Лимиты: 128 КиБ исходного сообщения, 220000 байт запроса, 500 ожидающих конвертов / 16 МиБ на получателя, 2000 регистраций, 500 контактов, 300 подписанных запросов за минуту на устройство. Доступ к чужим сообщениям по переданному ID невозможен: ID проверяется вместе с подписью.

## Криптография и пределы

На iOS используется реализация **HPKE Auth (RFC 9180)** из Apple CryptoKit: X25519 + HKDF-SHA-256 + ChaCha20-Poly1305. Для каждого конверта создаётся новый контекст с эфемерным ключом. Маршрут, UUID и время входят в AAD. HTTP-аутентификация и квитанции используют отдельный Ed25519-ключ.

Android использует совместимую реализацию HPKE Auth из Bouncy Castle 1.86. Идентичность и очередь зашифрованы ключом Android Keystore; проверены прямое расшифрование Apple CryptoKit ↔ Android и обмен через этот сервер.

Закрытые ключи, коды контактов, очередь и список уже принятых UUID сохраняются на телефоне в зашифрованном локальном хранилище. AES-GCM-ключ хранилища защищён Keychain `WhenUnlockedThisDeviceOnly`. Резервное копирование отключено. При потерянном файле идентичности для существующих сетевых данных новый ключ вместо старого не создаётся.

Это не Signal Double Ratchet: обновление ключей и forward secrecy при компрометации долговременного X25519-ключа получателя не реализованы. Удаление локальных данных меняет идентичность и требует нового обмена кодами. При удалении без интернета серверная очистка может не выполниться; удалённые конверты истекут по TTL. Удаление сообщения в интерфейсе очищает его локальную копию, а не копию собеседника.

Статус «Отправлено» означает принятие сервером. «Доставлено» означает сохранение приложением получателя и проверенную подпись квитанции; он не означает прочтение человеком. Автоматическая доставка на Android и iOS происходит только пока Mura открыта и разблокирована. Push / APNs / FCM и фоновая доставка не реализованы.

## Скачивание APK

Страница: https://defense-arthritis-maritime-salvador.trycloudflare.com/download

Прямой APK: https://defense-arthritis-maritime-salvador.trycloudflare.com/download/mura.apk

Публичные маршруты GET / HEAD разрешают только фиксированные файлы `server/public/index.html`, `mura.apk` и `SHA256SUMS`. База, код, ключи и логи не доступны. Служба `mac-service.py install` атомарно копирует эти файлы в папку службы и перезапускает только relay; работающий туннель сохраняет адрес. APK подписан постоянным release-ключом, закрытый ключ хранится отдельно от проекта. [Подпись Android](../docs/ANDROID_DISTRIBUTION.md).

Самостоятельный аудит безопасности, защита публичного сервера от распределённой атаки и эксплуатационный мониторинг не выполнялись. Для постоянной эксплуатации нужны обычные меры сопровождения и постоянный HTTPS-хостинг.

## Проверки

```sh
server/.venv/bin/python -m unittest discover -s server -v
MURA_TEST_RELAY_URL=http://127.0.0.1:8788 swift test --package-path ios/Core
```

Swift-проверки используют настоящие HPKE-конверты двух независимых идентичностей. Python-тесты проверяют подмену ID, replay, взаимное добавление, идемпотентность, права на квитанции, удаление и TTL. UI-тест в `ios/MuraUITests` проверяет iPhone и отдельную тестовую идентичность через публичный HTTPS-сервер, включая перезапуск приложения; два физических iPhone этими тестами не имитируются.

Первичные источники: [Apple HPKE](https://developer.apple.com/documentation/cryptokit/hpke), [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180), [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/), [Ed25519 в Cryptography](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/).
